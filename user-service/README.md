# user-service

Микросервис профиля покупателя учебного ecommerce-проекта (магазин парфюмерии). Хранит личные данные пользователя (имя,
телефон, email) и его адрес доставки. Аутентификация, регистрация, пароли и роли находятся в Keycloak, корзина живёт на
фронтенде, заказы и их история в order-service.

Stack: Java 21, Spring Boot 4, Spring Security OAuth2 Resource Server, Spring Data JPA, PostgreSQL, Flyway, Keycloak,
Lombok, MapStruct, Actuator

## Архитектура

```
Клиент ──► api-gateway ──► user-service ──► PostgreSQL (user-db)
                                │
                                └──► Keycloak (только ключи подписи JWT)
```

- Наружу через gateway доступны только `/api/users/**` (маршрут с CircuitBreaker, как у остальных сервисов).
- User-service ходит только в Keycloak (ключи проверки JWT) и в свою PostgreSQL. Других сервисов он не вызывает и
  событий не публикует.
- К базе Keycloak сервис не подключается: источником данных о пользователе служит токен.

## Что входит в сервис, а что нет

| Входит                                         | Не входит                                             |
|------------------------------------------------|-------------------------------------------------------|
| Профиль: имя, фамилия, телефон, email          | Регистрация, логин, пароли (Keycloak)                 |
| Один адрес доставки на пользователя            | Создание менеджеров и выдача ролей (консоль Keycloak) |
| Одинаковая работа для покупателей и менеджеров | Корзина (на фронтенде)                                |
|                                                | История и отмена заказов (order-service)              |

## Доменные правила

- Идентификатор профиля это `sub` из токена Keycloak (`user_profile.id`). Связывать пользователей между системами не
  нужно.
- **`GET` ничего не пишет в БД.** Если профиля ещё нет, ответ собирается из claims токена (`given_name`, `family_name`,
  `email`), строка не создаётся.
- Профиль создаётся при первом сохранении: `PUT /api/users/me` или `PUT /api/users/me/address`. После создания он *
  *независим от Keycloak**: смена имени или email в Keycloak профиль не меняет.
- Все поля профиля и адреса необязательные.
- Телефон в формате E.164 (`+380501234567`), `email` в формате email.
- У пользователя **один адрес**. Удалить его нельзя, только очистить: обновить пустыми значениями (`null`, `""` или
  пробелы, всё это превращается в `null`).
- Значения адреса нормализуются: обрезаются пробелы по краям и схлопываются повторяющиеся внутри.
- Адрес заполняется целиком: `city` и `addressLine` обязательны вместе, а `postalCode` допустим только вместе с ними.
  Все три пустые это валидная очистка адреса.
- Страна не хранится (учебный проект для Украины), способ доставки в сервисе не моделируется.
- Конкурентные изменения защищены оптимистичной блокировкой (`@Version`), при конфликте `409 CONCURRENT_MODIFICATION`.
- Если два первых сохранения профиля одного пользователя придут одновременно, второе получит `409 CONFLICT` и должно
  быть повторено клиентом.

## API

Все эндпоинты требуют `Authorization: Bearer <JWT>`. Пользователь определяется по `sub`, поэтому чужие данные недоступны
по построению: в путях нет идентификаторов.

| Метод | Путь                    | Описание                                                             |
|-------|-------------------------|----------------------------------------------------------------------|
| GET   | `/api/users/me`         | Профиль вместе с адресом. Если профиля нет, данные берутся из токена |
| PUT   | `/api/users/me`         | Создаёт или обновляет профиль и (необязательно) адрес                |
| GET   | `/api/users/me/address` | Адрес пользователя (при пустом все поля `null`)                      |
| PUT   | `/api/users/me/address` | Заменяет адрес, не трогая поля профиля                               |

### Семантика `PUT /api/users/me`

- Поля `firstName`, `lastName`, `email`, `phone` заменяются целиком: `null` очищает поле, поэтому фронтенд должен
  отправлять полный объект.
- Поле `address` необязательное: **если ключа нет (`null`), адрес не меняется**, объект заменяет адрес целиком (пустые
  значения очищают).
- При ошибке валидации адреса не сохраняется ничего, в том числе поля профиля из того же запроса.

Пример ответа:

```json
{
  "firstName": "Alex",
  "lastName": "Test",
  "email": "alex@example.com",
  "phone": "+380501234567",
  "address": {
    "city": "Kharkiv",
    "addressLine": "Sumska 1, apt 5",
    "postalCode": "61000"
  }
}
```

Объект `address` присутствует в ответе всегда. Если адрес не заполнен, у него все поля равны `null`, поэтому «адрес
заполнен» проверяется по `address.city != null`.

### Работа фронтенда на странице заказа

Сервис не участвует в оформлении заказа, предзаполнением формы занимается фронтенд:

- форма заказа предзаполняется из `GET /api/users/me` (имя, телефон, адрес), пользователь может заменить любые значения;
- заказ хранит **снимок** данных доставки, а не ссылку на профиль или адрес;
- если адрес в профиле пуст, после успешного заказа фронтенд сохраняет адрес из формы через `PUT /api/users/me/address`;
- если адрес в профиле уже есть, данные из формы заказа его не перезаписывают.

### Модель данных

Таблица `user_profile`:

| Поле                                        | Описание                                       |
|---------------------------------------------|------------------------------------------------|
| `id`                                        | UUID, равен `sub` из Keycloak (первичный ключ) |
| `first_name`, `last_name`, `email`, `phone` | Личные данные                                  |
| `created_at`, `updated_at`                  | Аудит                                          |
| `version`                                   | Версия для оптимистичной блокировки            |

Таблица `user_address` (связь 1:1 с профилем):

| Поле                                  | Описание                                                                               |
|---------------------------------------|----------------------------------------------------------------------------------------|
| `profile_id`                          | UUID, одновременно первичный и внешний ключ на `user_profile.id` (`ON DELETE CASCADE`) |
| `city`, `address_line`, `postal_code` | Поля адреса                                                                            |
| `created_at`, `updated_at`, `version` | Аудит и версия                                                                         |

Схема создаётся миграциями Flyway (`src/main/resources/db/migration`), Hibernate работает с `ddl-auto: validate`.

## Безопасность

- Сервис проверяет JWT от Keycloak (`issuer-uri` для проверки `iss`, `jwk-set-uri` на внутренний адрес Keycloak в сети
  compose).
- Роли берутся из `realm_access.roles` и получают префикс `ROLE_`. Роли для эндпоинтов не требуются: профиль есть и у
  покупателей, и у менеджеров.

| Доступ                              | Правило                                    |
|-------------------------------------|--------------------------------------------|
| `/api/users/**`                     | любой аутентифицированный пользователь     |
| `/actuator/health/**`               | публично                                   |
| `/v3/api-docs/**`, `/swagger-ui/**` | публично (включено только в профиле `dev`) |
| всё остальное                       | аутентифицированный пользователь           |

Ответы 401 и 403 приходят в том же формате, что и остальные ошибки.

## Формат ошибок

Все ошибки возвращаются в формате RFC 9457 (`application/problem+json`) через `ApiProblem`. В ответе есть код ошибки (
`ErrorCode`), `traceId` запроса, `source` (`user-service`) и, для валидации, список полей с ошибками (для вложенного
адреса поля имеют вид `address.city`).

Основные коды: `VALIDATION_FAILED`, `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT`, `CONCURRENT_MODIFICATION`,
`SERVICE_UNAVAILABLE`, `INTERNAL_ERROR`.

**Логирование.** Ошибки логируются в одной точке, в `GlobalExceptionHandler`:

- 5xx: `ERROR` со стеком;
- 4xx: `WARN` одной строкой (метод, путь, статус, класс исключения).

## Конфигурация

Настройки задаются переменными окружения (в compose они уже заданы).

| Переменная                                                                         | Назначение                                                                   |
|------------------------------------------------------------------------------------|------------------------------------------------------------------------------|
| `SERVER_PORT`                                                                      | Порт сервиса (`8085`)                                                        |
| `USER_DB_HOST`, `USER_DB_PORT`, `USER_DB_NAME`, `USER_DB_USER`, `USER_DB_PASSWORD` | PostgreSQL сервиса (`user-db`)                                               |
| `JWT_ISSUER_URI`                                                                   | Значение `iss` в токенах Keycloak (`http://localhost:8180/realms/ecommerce`) |
| `JWT_JWK_SET_URI`                                                                  | Адрес ключей Keycloak внутри сети Docker                                     |
| `USER_SERVICE_URL` (в api-gateway)                                                 | Адрес сервиса для маршрута gateway (`http://user-service:8085`)              |
| `SPRING_PROFILES_ACTIVE`                                                           | `dev` включает OpenAPI. Без профиля режим прод-подобный                      |

Секреты (`USER_DB_*`) хранятся в корневом файле `.env` проекта (в репозиторий не коммитится). Секрета для Keycloak
сервису не нужно: он никого не вызывает.

## Запуск

Из корня проекта:

```
docker compose up -d --build user-db user-service
docker compose ps
```

Через gateway сервис доступен по `http://127.0.0.1:8080/api/users/...`. Чтобы изменения в маршрутах gateway
подхватились, пересобери и его (`docker compose up -d --build api-gateway`).

### Dev-порты на хосте

| Сервис               | Адрес                   |
|----------------------|-------------------------|
| api-gateway          | `http://127.0.0.1:8080` |
| user-db (PostgreSQL) | `127.0.0.1:5435`        |
| Keycloak             | `http://127.0.0.1:8180` |

Используй `127.0.0.1`, а не `localhost`: на Windows `localhost` сначала резолвится в IPv6 и добавляет ~200 мс.

### Сброс базы

Если миграции были изменены задним числом, Flyway упадёт на несовпадении контрольных сумм. На dev-окружении базу проще
пересоздать:

```
docker compose stop user-service user-db
docker compose rm -f user-service user-db
docker volume ls
docker volume rm <имя_тома_с_user-db-data>
docker compose up -d --build user-db user-service
```

### Получение токена для проверок

```
curl --location 'http://localhost:8180/realms/ecommerce/protocol/openid-connect/token' \
--header 'Content-Type: application/x-www-form-urlencoded' \
--data-urlencode 'grant_type=password' \
--data-urlencode 'client_id=ecommerce-dev' \
--data-urlencode 'username=customer' \
--data-urlencode 'password=<TEST_USER_PASSWORD>'
```

Токен живёт 5 минут. У `customer` нет ролей, у `testuser` есть менеджерские: профиль работает одинаково.

### Сборка

```
mvn clean package
```

## Регистрация пользователей

Регистрация целиком происходит в Keycloak (`registrationAllowed: true`, клиент `ecommerce-web` с PKCE). User-service о
ней не уведомляется, и строка профиля при регистрации не создаётся: она появится при первом сохранении, а до этого
`GET /api/users/me` отдаёт данные из токена. Менеджеров создаёт администратор в консоли Keycloak (Users → Add user,
затем Role mapping).

## Наблюдаемость

- **Health:** `/actuator/health`, а для compose `/actuator/health/readiness` (включает PostgreSQL).
- **Трассировка:** Micrometer Tracing кладёт `traceId` и `spanId` в MDC, поэтому они есть в строках лога и в теле
  ошибки. Экспорт во внешние системы выключен.

## Планы и ограничения

- Синхронизации с Keycloak нет: удаление или блокировка пользователя в Keycloak не затрагивает его профиль и адрес.
- Подтверждение email и восстановление пароля в realm выключены (`verifyEmail: false`, `resetPasswordAllowed: false`),
  их стоит включить вместе с настройкой SMTP, когда появится notification-service.
- Для notification-service email пользователя лучше передавать в событиях заказа, а не опрашивать user-service.
- Вход через Google и GitHub добавляется как Identity Provider в realm (для GitHub email может прийти пустым, профиль к
  этому устойчив).
- При желании создавать профиль сразу при регистрации понадобится event listener в Keycloak и consumer в user-service,
  сейчас это избыточно.
- Интеграционные тесты (Testcontainers: PostgreSQL) не написаны.
